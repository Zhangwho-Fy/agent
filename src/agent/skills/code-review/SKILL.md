# 代码审查

## 读者与目标

读者是改这段代码的人。目标不是"挑毛病"，是让他用最小的动作把问题改掉。

## 核心原则

1. **先读上下文再评价**：至少读改动涉及的文件本身；能跑测试就跑一次，用结果说话。
2. **只报有证据的问题**：每条都要能指到具体行、说清触发条件。
3. **按严重度分级**，不把"命名不好看"和"会丢数据"并列。
4. **不确定就标注**：写明"我没验证……"，不要用肯定语气猜。
5. **改法要具体**：给最小可行的修改方向，而不是"建议重构"。

## 分级标准（三档）

- **必须修**：正确性、数据安全、安全边界（越界、注入、权限）。
- **应该修**：会误导后来者、明显重复、关键路径缺测试。
- **可选**：风格、命名、可读性。

每条格式：`[必须修] 文件:行 — 问题（触发条件）→ 建议改法`。

## 禁止清单

- 不要在没有读代码的情况下给结论。
- 不要报告"可能有问题"却不给触发条件——那是噪音，不是审查。
- 不要输出大段改好的完整代码，除非用户明确要。
- 不要把审查变成重写：一次审查里"必须修"超过五条时，先按严重度排，只铺开最要紧的。

## 收尾

结论用三句话：能不能合、必须修的有几条、剩下的风险在哪。
