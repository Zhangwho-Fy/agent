# Agent 设计文档

> 本文是**规划层**：做什么、不做什么、分几期、怎么验收。
> 技术细节（选型、架构、目录结构、接口、数据模型、配置、测试策略）见 [detailed-design.md](./detailed-design.md)。

## 1. 目标与非目标

### 目标

1. **代码库助手（主场景）**：在本地仓库上读代码、跑命令、改文件，闭环解决真实任务。
2. **聊天（兼有）**：同一个内核支持纯对话模式（`profile=chat`），不要求有仓库。
3. **"部分生产可用"的证据链**：可持久化、可恢复、可重放、可评测，且失败模式有文档。

### 非目标

- 不做多 Agent 编排框架
- 不做桌面端、移动端客户端（需要时作为独立项目考虑）
- 不做多用户 / 多租户 / 云部署
- 不做自己的模型训练或本地推理
- 不引入 LangChain 这类 agent 框架（主循环就是本项目的价值）

## 2. 架构概览

```
   CLI（瘦客户端）
        │
        ▼
   agent serve（本地长驻进程）
      ├─ server:    HTTP + SSE
      ├─ core:      loop / 事件模型 / prompt
      ├─ tools:     执行 + 审批 + 沙箱
      ├─ retrieval: 代码检索（词法 + 向量）
      ├─ store:     SQLite 会话与事件持久化
      └─ providers: 模型适配 ──> 模型 API（或录制回放）
              │
              └──> 本地仓库 / git / 测试 / 编译器
                   └── C++ MCP server（可选，可降级）
```

### 三条不变量

1. **任务在服务端执行，客户端只是订阅者。** 客户端断线、退出不影响任务推进，重连后按 seq 补齐。
2. **工具只在有仓库的那台机器上执行**，且受工作区边界与审批策略约束。
3. **模型调用永远经过 Provider 抽象。** 线上走真实 API，测试走录制回放，CI 不花一分钱、不需要 key。

## 3. 里程碑

每个阶段结束时仓库都是**可运行、可演示**的，不留半成品；每阶段一次提交或几次小提交。

| 阶段 | 交付物 | 结束时能演示什么 |
| --- | --- | --- |
| 1. 最小闭环 | tool-calling loop、3 个工具、流式输出 | 让它读文件/跑命令回答问题 |
| 2. 变成系统 | SQLite 会话持久化、结构化 trace | 杀掉进程重启，会话还在、能续跑 |
| 3. 工程化 | Provider 抽象、录制回放、pytest 评测集、CI | 不花一分钱跑回归 |
| 4. 服务化 | HTTP + SSE + CLI、协议文档冻结 | `curl` 走完一次完整会话 |
| 5. 检索（RAG） | 符号切块 + FTS5 索引 + 混合检索 + 检索评测 | 给出 recall@5 前后对比数据 |
| 6. 扩展 | MCP client、C++ MCP server | 接第三方工具、C++ 模块降级不影响功能 |

## 4. 验收标准

### 阶段验收

1. **最小闭环**：一条命令让它回答"`xxx.py` 里那个函数做了什么"，终端可见流式输出和工具调用；工具报错能被模型看到并自我纠正一次。
2. **变成系统**：任务跑到一半 `kill -9`，重启后历史完整；`agent replay <trace>` 能按顺序还原全部事件，**不调用模型**。
3. **工程化**：`pytest` 全绿；`pytest eval` 输出 golden 集通过率；**不设置 API key 也能跑**（录制回放）；CI 上有一次绿色构建。
4. **服务化**：只用 `curl` 走完"建会话 → 发消息 → SSE 收流 → 审批一次写操作 → 拿结果"；断线重连按 `Last-Event-ID` 补齐不丢不重；同一条消息发两次不重复执行工具。
5. **检索**：给出 recall@5 / MRR；纯词法 / 纯向量 / 混合三种配置的实测对比写进 README。
6. **扩展**：接一个现成 MCP server 当工具源；C++ MCP server 不启动时自动降级且功能不受影响。

### 项目终验（面试现场能当场演这四件事）

1. 真实任务端到端跑通（真实仓库、真实修改、真实测试通过），全程可回放。
2. 断流后重连续传。
3. `agent replay` 离线还原历史会话。
4. 讲清威胁模型：哪些命令会被拒绝、密钥为什么不在客户端、工具输出为什么必须截断。

### 明确不算达标

不追求覆盖率数字好看；不追求支持多家 provider（一家 + 一个 replay 实现即可，接口留好）；不追求工具数量多。

## 5. 分工与协作方式

- **[我]**：框架、store、server、测试、样板、CLI、检索实现、文档。
- **[你]**：core loop 主体、工具执行与审批策略、评测任务设计、每个阶段的 review。
- 每个小步：先讲设计意图与涉及的知识点（用 C++ 对照的讲法），再给代码，讲完你 review，有疑问当场改。
