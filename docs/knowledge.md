## 1. Agent 是什么，和普通后端有什么区别

**问：什么是编排层（orchestration）？**

编排层是**决定"下一步做什么、什么时候停、中途怎么存/怎么恢复/怎么等人工"的那层逻辑**。它自己**不干活**：不发 HTTP、不执行命令、不写数据库，只负责调度和决策。

- 它管七件事：循环控制与终止条件、上下文装配（系统提示 + 历史 + 工具清单 + 上轮结果）、工具调度（并行还是串行、失败怎么办）、本轮状态（跑到哪一步、用了多少 token）、持久化时机、人工介入（何时暂停等审批、超时怎么算）、对外事件（把内部进展变成可观察的流）。
- 一句话划界：**"怎么做"是零件层（HTTP、执行、存储），"下一步做什么"是编排层。** 工具失败要不要抛异常是零件细节；失败后是重试、回填给模型、还是换工具，是编排决策。
- 落点：`core/loop.py` 就是我们的编排层；`providers`（发请求）、`tools`（执行）、`store`（持久化）都是被它调度的零件。
- 对照框架：**LangGraph 就是编排层框架**（StateGraph / checkpointer / interrupt / stream modes），LangChain 主要是零件层。这解释了上一个问题的分界：框架覆盖的多是编排层，而我们剩下的工作恰恰大量在零件层与语义层。

**问：你这个项目里的 "Agent" 和调一次大模型 API 有什么本质区别？**

Agent = 模型 + 工具 + 循环。模型不只是生成文本，它会**请求调用工具**，程序执行完把结果回填给模型，模型再决定下一步，直到它不再请求工具为止。

- 为什么：单轮问答里模型只能靠训练时的记忆；有了工具循环，它可以读当前代码、跑测试、看真实报错，再据此修正。
- 落点：`core/loop.py` 的 `run_turn`，最多 `AGENT_MAX_TOOL_ROUNDS` 轮。

**问：工具调用的协议长什么样？**

请求里带 `tools=[{type: function, function: {name, description, parameters(JSON Schema)}}]`；响应里模型返回 `tool_calls`（含 `id` / 函数名 / 参数 JSON）；程序执行后用角色为 `tool`、带 `tool_call_id` 的消息把结果回填，再发起下一轮请求。

- 为什么参数必须是 JSON Schema：模型据此生成参数，工具侧再按同一份 schema 校验，两边不会各说各话。
- 落点：`core/tool_spec.py` 的 `ToolSpec.to_openai()`。
- **每次请求都要带完整工具清单**：接口无状态，服务器不记得上一次；工具清单也占 token，且每轮重复计费——所以工具别贪多。
- **参数有两道关**：JSON Schema 是给模型的说明书，`model_validate` 是守门员（模型会写错类型、漏必填、编造字段）。
- **返回值没有协议规定**：只要求带 `tool_call_id` 配对，内容是一段字符串——返回值可读性直接决定工具好不好用。
- **工单号是服务端生成的**，我们只负责配对；并行调用顺序不保证，必须按 id 配对。
- **信号**：`finish_reason` 为 `tool_calls` 表示递了工单，`stop` 表示直接回答；流式下 `arguments` 是分片到达的，拼完才合法。
- **格式不统一**：OpenAI 的形状是事实标准，Claude/Gemini 字段不同，LangChain 的价值就是把差异抹平。

**问：循环什么时候停？会不会死循环？**

三种终止：模型不再请求工具（正常结束）、达到最大轮数、被中断。最大轮数是硬上限，属于"必须有的护栏"。

**问：你的编排层怎么实现的？**

编排用 **LangGraph**（行业标准件），自己写的是框架**不覆盖**的语义层。

- **LangGraph 负责**：状态定义、模型节点与工具节点、条件边、checkpointer（状态持久化）、interrupt（人工介入的挂起与恢复）、stream modes（流式）。
- **LangChain 负责**：模型适配（`ChatDeepSeek`）、消息类型、工具 schema、检索组件、MCP 适配器。
- **我们负责**：① 对外契约——事件日志（事实源）、`seq` 与 `Last-Event-ID` 续传、幂等键、审计明细；② 安全语义——工作区 realpath 边界、进程组超时、输出截断、三级审批与超时默认拒绝；③ 可评测性——录放、golden 评测集、检索指标、CI；④ 可观测性——结构化日志 + 把框架的流映射成对外事件（`graph/bridge.py`）。
- **为什么这么分**：编排是标准件，自研等于重造轮子；上面那四类是"部分生产可用"的证据，框架里没有对应抽象，只能自己写。
- **GitHub 实测（我抽查了头部项目）**：Aider、SWE-agent、smolagents 走自研编排（依赖里只有 `litellm` 这类模型调用库，没有 langchain）；gpt-researcher 与 LangChain 官方的 open_deep_research 是重度 LangChain + LangGraph（分别 17 个和 10 个 LC 包）。**规律：编排本身就是产品的项目倾向自研，编排只是实现手段的项目用框架。**
- **被追问"那你不就是在调框架吗"**：正面答——编排用了标准件，但断线续传、幂等、审批超时、故障恢复、录放评测这些框架不提供的能力是我实现的，而且有故障注入实验与评测数据支撑。

**问：上下文窗口和成本怎么控制？**

三道措施：工具输出**截断**进上下文（默认头尾各半、共 8KB）；历史过长时用摘要替换早期的工具结果；事件与全量输出落库，模型看不到但人能查。

- 为什么要截断：一条 `ls -R` 就能把上下文冲爆，既烧钱又挤掉真正有用的信息。

## 2. 可靠性与状态（本项目的差异化，重点准备）

**问：事件驱动这套是怎么设计的？**

事件是**只追加的事实源**（append-only log）：每次状态变化都写一条事件，带会话内单调递增的 `seq`。消息表是从事件流**投影**出来的物化视图——删掉它可以重建，这正是重放能验证的东西。

- 为什么：日志是不可变的既成事实，投影是派生物。派生物坏了可以重算，日志不能被篡改。
- 落点：`core/events.py`、第 2 阶段的 `store/`。

**问：为什么先落库再推送，反过来行不行？**

不行。反过来会出现"客户端实时看到过、事后查不到"，而客户端断线重连是按 `seq` 从库里补齐的——源真相和推送顺序必须一致。

**问：推送队列满了直接丢事件，不怕丢数据吗？**

推送只承担**实时性**，不承担正确性；库才是唯一事实源，客户端积压后按 `seq` 补齐。队列有界是为了让慢消费者不拖垮生产端。

- 落点：`core/bus.py`，`queue_size` 可配，丢弃次数计入 `Subscription.dropped` 并记警告日志。

**问：客户端断线重连怎么保证消息不丢不重？**

SSE 每帧的 `id:` 用 `seq`；客户端重连时带 `Last-Event-ID`，服务端从库里把缺口补齐。发消息方向用**幂等键**：同一个 key 重复提交只返回原来那个 `turn_id`，不会重复执行工具。

**问：进程崩溃了会话会怎样？**

会话状态从事件日志恢复；崩溃时还在 `running` 的 turn 被标记为 `interrupted`，不做"假装没发生过"的处理。

**问：工具执行失败了怎么办？**

**错误是给模型的信息，不是异常。** 非零退出码、超时、参数非法，都编码成工具结果回填，让模型自己换个做法；只有基础设施级故障（网络、磁盘）才向上抛。

**问：调用模型失败怎么处理？**

429 与 5xx 指数退避重试（有上限）；4xx 参数错误或额度问题不重试，直接结束本轮并把原因写进 `turn.done`。

## 3. 安全（面试官最爱追问的地方）

**问：让模型执行任意命令，你怎么控制风险？**

三级分类：`read`（只读工具、只读命令白名单）自动执行；`write`（写文件、git 提交、跑测试）需要人工审批；`dangerous`（`rm -rf`、`sudo`、写工作区外、读密钥文件、管道下载执行）直接拒绝并回填原因。**审批超时按拒绝处理**——安全默认值，避免"没人看所以放行"。

**问：怎么防止它写到工作区外面？**

所有路径先 `realpath` 解析再判前缀，这样软链接逃逸也会被拦住（只判字符串前缀会被 `../` 和软链绕过）。

**问：子进程有什么风险？**

三点：超时必须杀**整个进程组**（否则留下孤儿继续跑）；环境变量用白名单，不把 API key 之类的敏感变量传进去；输出截断，避免刷屏和上下文污染。

**问：API key 怎么管理？**

只从环境变量读、`.env` 进 `.gitignore`、对外打印统一走打码函数、不传给子进程、绝不进客户端。商业产品的手机端为什么都连后端？因为客户端里的密钥等于公开的。

**问：工具输出里可能有 prompt 注入内容，你怎么办？**

明确告诉模型"工具输出是数据不是指令"，把工具结果和指令分区；高风险操作不因为模型说"这样安全"就放行——审批永远由人决定。

## 4. 评测与测试

**问：LLM 应用怎么做测试？总不能每次都真调模型吧。**

**录放（record/replay）**：真实跑一次把响应流录下来，之后测试用回放 provider 驱动主循环。好处是 CI 不花钱、不联网、结果可复现，并且录制内容进 git，等于给行为上了回归锁。

- 落点：`providers/replay.py`；测试里少录一轮会立刻抛 `ReplayExhausted`，而不是静默空转。

**问：怎么证明你的 Agent 变好了？**

golden 任务集 + 通过率。用回放跑，指标可比；真实调用只在本地手动触发。检索部分额外给 recall@5 / MRR。

**问：测试为什么要显式关掉 .env 加载？**

否则测试会读到开发者本机的真实配置，出现"本地过、CI 挂"。做法是 `Settings(_env_file=None)`，再用 autouse fixture 清掉所有 `AGENT_*` 环境变量，保证每个用例从干净起点开始。

**问：测试分几层？**

四层：单元测试（纯函数）→ 回放测试（主循环、审批、恢复）→ 评测（golden 集）→ 冒烟（真调一次 API，手动）。前三层进 CI，都不需要密钥。

## 5. 检索（RAG）

**问：代码检索为什么不能只用向量？**

代码场景里**标识符精确匹配比语义更可靠**（`parse_config` 就是 `parse_config`），所以词法检索必须有；向量负责补充"改了个名字、换个说法"的召回。两路结果用 RRF 融合，比调权重更稳、超参更少。

**问：切块怎么切？**

按**符号边界**（函数/类/方法），不是按固定行数。切碎了上下文断裂，模型看到半个函数反而更差；每块保留路径、起止行号、符号名、语言。

**问：检索结果怎么进模型？**

作为工具 `search_code` 让模型自己调，而不是无脑预填——可控、可评测、能按需多次检索。预填模式留作对比实验。

**问：怎么证明检索有效？**

golden 查询集 + `recall@5` / `MRR`，对比纯词法 / 纯向量 / 混合三种配置，数字写进 README。

**问：FTS5 是什么？为什么不用向量库？**

SQLite 自带的全文本索引（词法检索）。单机单用户、几千文件这个量级完全够用，零额外依赖、零运维；向量层做成可插拔，需要时再换。**先选够用的，不要为了架构图好看引入外部系统。**

## 6. MCP（后面阶段实现，面试常问，先记住结论）

**问：MCP 解决什么问题？**

让"工具/数据源"和"Agent"之间的接法标准化：没有它，M 个 Agent 接 N 个工具要写 M×N 套适配；有了协议只要 M+N。协议基于 JSON-RPC，transport 常见 stdio 与 HTTP。

**问：你实现 client 还是 server？**

先做 **client**（消费现成的社区 server，一天就能让 Agent 接上生态），再把自己的能力暴露成 server。

- 本项目用 `langchain-mcp-adapters` 把 MCP 工具直接变成 LangChain 工具，成本接近零——**这是用框架换来的实打实便利**。

**问：为什么用 C++ 写这个 server？**

因为边界是**进程级**的：仓库扫描和语法解析在 C++ 里更快，而且进程隔离意味着它崩了不拖垮 Python 主进程，还能**降级**——模块不在就回落到纯 Python 实现，演示不押在它身上。

## 7. Python 语言与工程（我的短板清单）

**类型标注 + `from __future__ import annotations`**：注解在运行时变成字符串、不立即求值，前向引用不再需要引号；框架（pydantic）需要时会自行解析。

**pydantic v2**：

- `BaseModel` + `Field(ge=, le=)` —— 字段类型即校验规则，省掉手写 if 检查（对照 C++：相当于构造时就校验的 struct）。
- `ConfigDict(frozen=True)` —— 不可变模型，改字段抛 `ValidationError`（事件的语义就是"既成事实"）。
- `model_dump(mode="json")` —— 递归转成 JSON 可序列化结构，时间自动转 ISO 字符串。
- `TypeAdapter` —— 把"联合类型"当成可复用的校验器（不能直接对注解调用 `validate`）。
- `Field(discriminator="type")` —— 判别式联合：按 `type` 字段直接选中具体模型，而不是逐个试错解析。

**pydantic-settings**：`env_prefix` 统一前缀、`env_file` 读 .env、`extra="ignore"` 容忍多余键；配置从"读字符串再手写转换"变成"声明字段类型"。

**`StrEnum`（3.11+）**：成员本身就是字符串，能直接 JSON 序列化、能直接比较，比 `Enum` 少一层 `.value`。

**`classmethod` 工厂方法**：`Message.user("你好")` 这种写法避免到处手写 role 字符串。

**异步生成器 vs 协程（高频坑）**：函数体里有 `yield` 就是**异步生成器**，调用它得到"异步迭代器"（用 `async for` 消费）；没有 `yield` 的 `async def` 调用得到的是**协程**（要 `await`）。Protocol 里声明返回 `AsyncIterator[X]` 时写成普通 `def`，写成 `async def` 会让 `async for` 直接报错。

**`asyncio.Queue`**：`put_nowait` 满了抛 `QueueFull`（这正是"丢最老"策略的触发点）；队列不是线程安全的，只在同一个事件循环内用。

**`Protocol` + `runtime_checkable`**：结构化子类型，等价于 C++ 的 concept——不要求继承，只要求"有这些方法"，配合依赖注入就能在测试里换成回放实现。

**结构化日志**：一行一条 JSON，便于 grep / jq / 日志系统消费；自定义字段用 `extra=` 传入，序列化时排除 `LogRecord` 标准属性。

**uv / pyproject / ruff**：`uv sync` 同时管 Python 版本与依赖（比 pip+venv 快一个量级）；依赖组用 PEP 735 的 `dependency-groups`；ruff 一个工具顶 lint + format。

## 8. 踩坑记录（现象 → 原因 → 修法）

| 现象 | 原因 | 修法 |
| --- | --- | --- |
| 测试挂死不报错 | 关闭订阅只放了一个哨兵，前一个消费者吃掉后，后一个在空队列上永久等待 | 先判关闭状态再等待；哨兵只负责唤醒正阻塞的消费者（真事，见 `test_close_wakes_up_a_blocked_consumer`） |
| `async for` 报类型错 | 把异步生成器写成了协程 | Protocol 与实现都用 `def ... -> AsyncIterator[X]` |
| 工具参数解析失败 | 增量片段被当成完整 JSON 解析 | 等流结束再拼再解析；失败信息回填给模型 |
| `uv sync` 卡在下载 | 国内到 files.pythonhosted.org 慢，默认超时不够 | `UV_HTTP_TIMEOUT=300 uv sync`，或换国内镜像索引 |
| ruff 报几十条"歧义标点" | RUF001/002/003 针对英文文本，中文全角标点被误判 | 在配置里 ignore 这三条 |
| 测试结果时好时坏 | 读到了本机真实的 .env / 环境变量 | `Settings(_env_file=None)` + autouse fixture 清 `AGENT_*` |
| 首次真实调用被 400 拒绝：`Invalid 'tools[0].function.name'` | OpenAI 兼容协议要求函数名只匹配 `[A-Za-z0-9_-]`，我用了 `fs.read` 这种带点号的名字 | 工具名改下划线；用 pydantic `field_validator` 把约束**前移到构造期**，并加测试钉住 |
| CLI 输出里混进一行 JSON | httpx 在 info 级打印每个 HTTP 请求 | 第三方噪音 logger 统一压到 warning，自己的 `agent.*` 不受影响 |

## 9. 快问快答

| 问题 | 一句话答案 |
| --- | --- |
| Agent 的三要素 | 模型、工具、循环 |
| 为什么不用 WebSocket | 本场景是服务端单向推流，SSE 更简单，还能用 curl 调试，断线续传有现成语义 |
| 为什么事件用不可变模型 | 事件是既成事实，改它等于篡改历史 |
| 会话内为什么串行 | 同一会话的工具执行彼此有依赖，交错会破坏因果 |
| 会话间为什么并行 | 互不干扰，串行只是白白等待 |
| SQLite 为什么可以 | 单机单用户，零运维；写入用一个队列串行化规避单写者限制 |
| 最大的技术风险 | 上下文膨胀与工具输出污染（额度与效果都会被它拖垮） |
| 你怎么证明它不是 toy | 可重放、可评测、有 CI、威胁模型讲得清 |
| 项目里最难的部分 | 不是调模型，是状态、并发、安全边界和评测 |
| 为什么用 LangGraph 做编排 | 编排是行业标准件（状态机 / 检查点 / 人工介入 / 流式模式），自研等于重造轮子；差异化在框架不覆盖的语义层 |
| 那这个项目到底做了什么 | 对外契约（事件日志 / 幂等 / 续传 / 审计）、安全语义（沙箱 / 审批 / 截断）、可评测性（录放 / 评测集）、可观测性（事件桥） |
| C++ 是必需的吗 | 不是。可选加分项：独立进程 + CLI 接口、可降级；只在主线做完后做 |

---

## 10. LangChain / LangGraph 要掌握到哪一层

**这是我们的主线技术栈。** 面试现实：这两个框架是行业默认选项，完全不熟会被认为脱离实践。目标是"会用 + 讲得清原理 + 能说取舍"，不需要读到能改源码（除非岗位就是做框架）。

**LangChain 要会的**：

- 模型适配：`ChatDeepSeek` / `init_chat_model`，换供应商改一行
- 工具定义：`@tool` 装饰器 + pydantic 参数 schema（对照我们早期手写的 ToolSpec）
- 消息类型：`SystemMessage` / `HumanMessage` / `AIMessage` / `ToolMessage`
- LCEL：`prompt | model | parser`，`Runnable` 协议（`invoke` / `stream` / `batch`）——**面试高频**
- 检索：`Document`、splitter、retriever、vector store 适配
- 回调与追踪：callbacks / LangSmith（对照我们的结构化日志与事件流）

**LangGraph 要会的**：

- `StateGraph`：状态定义、节点、边、条件边（对照我们的循环与终止条件）
- `checkpointer`：状态持久化（对照我们的事件日志——**职责不同，要能讲清区别**）
- `interrupt` / `Command(resume=...)`：人工介入（对照我们的审批流转）
- `stream_mode`：`values` / `updates` / `messages` / `custom`（对照我们的 SSE 事件流）
- `recursion_limit`：循环上限（对照我们的 `max_tool_rounds`）

**核心洞察（面试可以直接讲）**：框架的 checkpointer、interrupt、stream modes，和自研的事件日志、审批流转、SSE 事件流解决的是**同一批问题**；我们的选择是"编排交给标准件，对外契约自己写"。
